How it works

The same five steps sit behind every workflow. Where a language model helps and where plain code does the work is stated for each step.

The steps
  1. Collect: The workflow reads a fixed list of sources, or the entries and numbers you give it. A language model helps here, because sources are written in prose.
  2. Record: Each item is stored with its date, its source and a status: disclosed, stated by the company, opinion, inference, not disclosed or scheduled. Something that was left out is logged as a gap and is never filled in.
  3. Apply written rules: Scoring, rating and ranking come from rules that are shown before any result appears. This is plain code, so the same input gives the same output.
  4. Review: A named person approves, holds or overrules each result. The run waits for them. Every override is listed in the memo with its reason.
  5. Write the memo: One page, built from what was approved, with a source on every line.
Fixed and set per client
FixedThe five steps, the status labels, a source and a date on every item, gaps logged and not filled, and nothing released without approval.
Set with youThe topic, the source list, the standing decisions and the assumption behind each, the rating rules, the memo format, the schedule, who reviews, and where the memo is delivered.
Changes each runThe pages fetched, the events, the gaps, the flags, the ratings and the memo.
Kept between runsThe event ledger, the decision history and the review log. A live engagement keeps these. The examples on this site do not.
How you can check the work

A memo is only useful if you can see where each line came from, so every workflow is built around that.

  • Every item carries a date and a source link or reference, and a gap is shown as a gap.
  • In a live build, each quote a model extracts is checked against the fetched text, and a failure goes to the reviewer. The examples here do not fetch anything, so this check is a design requirement and not something you can try on this site.
  • The scoring and rating rules are written out on the page, and a reviewer can overrule the result.
  • You can ask for a back-test. Give me a past period where you know what happened, and we count what the workflow missed and what it got wrong.

Limits
  • A record is only as good as what goes into it. The workflows do not check an entry against the world.
  • The models are simple on purpose, and each page lists what it leaves out.
  • I do not claim a time saving or an accuracy figure for any workflow. A pilot would measure both.
